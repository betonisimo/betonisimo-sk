# Общие формы и редактор контента

Изменения подготовлены локально. GitHub, Vercel, рабочая база и рабочий Blob Store не изменялись.

## Что изменено

- Vzory и Doplnky используют один CatalogItemForm; цена есть только у Doplnky.
- Формы создания и редактирования используют одинаковые секции, поля, ошибки и кнопки.
- Блог и Realizácie используют BlockNote 0.55 (бесплатные компоненты, без аккаунта или платных расширений).
- Доступны H2/H3, абзацы, жирный/курсив/подчёркивание/зачёркивание, списки, перенос блоков, отмена/повтор и фотографии между абзацами.
- Для ссылки выделите слово/фразу и нажмите кнопку ссылки или Ctrl+K. Поддерживаются HTTPS, внутренние /пути и #якоря. В том же окне ссылка изменяется и удаляется.
- У каждой фотографии в тексте отдельные alt и видимая подпись. Обложки и отдельная галерея realizácie сохранены.
- Загрузка требует входа; сервер проверяет размер, MIME и сигнатуру JPG/PNG/WebP. Клиент сжимает фотографии до 1920 px и примерно 0,9 MB. SVG не принимается.
- Повторное нажатие сохранения блокируется. Во время загрузки фотографий сохранить или удалить запись нельзя.
- Slug существующей записи и первоначальная дата публикации не меняются при редактировании.

## Данные и совместимость

BlogPost.blocks сохраняется как JSON с version: 2 и массивом blocks. Старые массивы блоков поддерживаются при чтении и открытии в редакторе. Они преобразуются только при явном сохранении конкретной статьи. Массовой конвертации нет.

Для Project добавляется nullable-поле content JSONB. Старое description остаётся; для старых проектов служит исходным текстом, для новых сохранений автоматически получает обычный текст из редактора. Старые записи с content = NULL продолжают отображаться.

Публичный рендерер использует обычные React-элементы p, h2/h3, ul/ol/li, a, figure/figcaption. Произвольный HTML не исполняется, опасные URL отбрасываются. Редактор загружается только в админке. SEO-поля, canonical, JSON-LD, sitemap и исключение черновиков сохраняются.

## Перед будущим деплоем — обязательно

1. Сделайте резервную копию целевой базы. Git-ветка не является копией базы.
2. Проверьте, что выбрана правильная база, и отдельно примените SQL из prisma/manual-migrations/20260930_project_content.sql:

   ALTER TABLE "Project" ADD COLUMN IF NOT EXISTS "content" JSONB;

3. Только после появления поля разверните код. Команда build теперь выполняет prisma generate и next build, но НЕ prisma db push. Сборка больше не меняет схему базы автоматически.
4. Проверьте вход, старую статью и реализацию, создание/сохранение записи и реальную загрузку фото с рабочим BLOB_READ_WRITE_TOKEN.

Почему отдельный SQL: историческая папка Prisma migrations содержит только первоначальные три таблицы и не соответствует полной текущей схеме. Нельзя вслепую применять migrate deploy или добавлять в эту неполную цепочку миграцию, предполагающую наличие всех таблиц. Для полного управления миграциями сначала нужен отдельный baseline существующей базы.

Локальная .env не менялась. Обычный npm run dev будет использовать прежнюю DATABASE_URL; если там ещё нет Project.content, новые запросы Project завершатся ошибкой. Для работы без изменения рабочей базы используйте изолированную локальную тестовую базу.

Откат: добавленное nullable-поле не мешает прежнему коду. Но прежний редактор/рендерер не умеет читать version: 2 в BlogPost.blocks. После новых сохранений откат к старому коду требует совместимого рендерера либо восстановления затронутых статей из резервной копии. Поле content при откате не удалять.

## Проверки

Итог проверки 30.09.2026: 10 модульных тестов и 9 браузерных сценариев прошли; lint изменённых файлов и npm run build прошли. Проверены ширины 320, 390, 768 и 1280 px. Сборка и все записи выполнялись с отдельной локальной базой, не с Neon из .env.

На Windows перед prisma generate / npm run build остановите dev-сервер: иначе загруженный Prisma DLL может вызвать EPERM при генерации. После остановки тестового сервера итоговая полная сборка прошла.

- npm test — конвертация старых данных, JSON round-trip, форматирование, вложенные списки, URL, публикация, изображения, серверная валидация.
- npm run test:editor — Playwright, Edge, локальный сервер localhost:3100.
- npx next build — проверка production-сборки, без изменений базы.

E2E требуют отдельный PostgreSQL на 127.0.0.1:55439 с пользователем editor_test, DATABASE_URL=postgresql://editor_test@127.0.0.1:55439/postgres. Тесты откажутся запускаться с другим адресом базы. Перед началом на этой пустой базе применить prisma db push и запустить scripts/seed-editor-test.mjs.

Сервер для E2E запускается с переопределёнными переменными процесса:

- DATABASE_URL — адрес отдельной базы выше.
- ADMIN_USER=editor-local-test, ADMIN_PASS=editor-local-test-only.
- NEXTAUTH_SECRET и AUTH_SECRET — одинаковый отдельный тестовый секрет.
- NEXTAUTH_URL=http://localhost:3100.
- BLOB_READ_WRITE_TOKEN=local-test-disabled.
- npm run dev -- --hostname 127.0.0.1 --port 3100.

Эти настройки не предназначены для публикации. E2E используют существующее локальное изображение как фикстуру вместо отправки файлов в рабочее облачное хранилище. Успешная реальная загрузка в Vercel Blob без рабочего токена не проверялась; проверяются валидация, сжатие и обработка отказа.

## Отдельное замечание по зависимостям

npm audit сообщает уязвимости в существующем стеке, включая Next.js 16.2.4 и NextAuth 4.24.x. Массовое обновление Next.js, Prisma и авторизации в эту задачу не включалось; npm audit fix --force не запускался. Перед публикацией стоит отдельно проверить совместимые исправления и обновления.
